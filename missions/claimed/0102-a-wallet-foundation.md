The two genuinely open substrate items are the `octo-core` work — the workspace edge, the re-export, and the phase-out, in that order — and the identity store. The store is the larger of the two and is what RFC-0011-x addresses.

A note on what the store is **not**: it is not a new cryptographic feature. `Vault` already encrypts on disk with Argon2id and AES-256-GCM, `StarkliCompat` is a second independently tested encrypted keystore, and `IdentityKey` has a complete 41-test lifecycle. What is missing is a wiring layer plus the one thing no primitive supplies — anywhere to put an identity. Nothing in the workspace writes an `IdentityRecord`, so a reader alone would produce an always-empty store.

## Summary

Stand up `octo-wallet/` as a separate crate providing the user-facing wallet layer: Ed25519 identity substrate (RFC-0009), Stark Curve transaction substrate (RFC-0102), NodeType taxonomy, provider-key vault (file-per-slot on disk, Argon2id + AES-256-GCM, separate from identity keys), capability key derivation (HKDF-BLAKE3 with `cipherocto/cap/v1/` info string + audience DID as IKM), and starkli-compatible keystore import/export. `octo-core` re-exports wallet types via thin newtypes.

### Provider-key vault (RFC-0009 §Vault)

- [ ] `Vault` struct at `crates/octo-wallet/src/vault.rs` with `slots_dir: PathBuf` + in-memory `cache: HashMap<String, EncryptedBlob>`. **Partly phantom — the cache does not exist.** The shipped struct is `pub struct Vault { slots_dir: PathBuf }` and nothing else: no cache field, and no in-memory plaintext retention to justify one. `EncryptedBlob` is not a type in the workspace at all; the on-disk shape is `VaultFile { version: u8, salt: String, nonce: String, ciphertext: Vec<u8> }`. The `slots_dir` half of the criterion is met and the cache half was never built, and the absence is the better outcome — an in-memory `HashMap` of decrypted-or-decryptable blobs keyed by slot id is a second copy of the store's state to keep coherent with disk, for no measured gain. `Vault::list` reads the directory, so a cache would have bought nothing. Not carried as open.
- [ ] Slot files at `<slots_dir>/<slot_id>.vault` (hex-encoded slot_id; sanitized at API boundary to prevent path traversal)
- [ ] `Vault::put(slot_id, plaintext, passphrase)` — Argon2id(m=64MiB, t=3, p=4) → AES-256-GCM encrypt. The `flock(LOCK_EX)` half of this criterion **was never built**: there is no `flock` call and no `fs2` / `FileExt` import anywhere in `vault.rs`. The encryption half is landed and tested. Carried as an open concurrency concern, not as a phantom.
- [ ] `Vault::get(slot_id, passphrase, out) -> DecryptedHandle<'_>` — decrypts into the caller-owned `out` buffer. Three claims in the earlier form of this box are false and are corrected here. **`flock(LOCK_SH)` does not exist.** **mlock and VirtualLock do not exist** — verified absent from the whole workspace, not merely from this crate, so there is no at-rest locking story at all. **`DecryptedHandle` does not zeroize on drop**: it has no `Drop` impl, and it cannot, because it is `struct DecryptedHandle<'a> { bytes: &'a [u8] }` — a **borrowed slice**, holding no owned buffer to scrub. The zeroization that does happen is on two other objects, the derived AES key and the caller's `out` buffer, and it is unconditional rather than drop-triggered. LANDED for the decrypt-and-return shape; the locking and the drop-scrub are open.
- [ ] `Vault::list() -> Result<Vec<String>, WalletError>` — slot IDs only, no plaintext. The `Result` is part of the real signature; the earlier form dropped it, and a caller written against that form would not compile.
- [ ] Error variants live on `WalletError` in `crates/octo-wallet/src/error.rs`, **not** on a `VaultError` enum — `WalletError` is the single crate-wide error type and there is no `VaultError` in the tree. The five variants this box names map onto it as `VaultSlotNotFound(String)`, `VaultDecryptionFailed`, `VaultKdfTimeout`, `Io(#[from] std::io::Error)`, `InvalidSlotId(String)`. Two of the five names are right and gained a payload; three were renamed with a `Vault` prefix. LANDED, modulo the naming drift.
- [ ] Test: save → reload → same key bytes
- [ ] Test: wrong passphrase → `WalletError::VaultDecryptionFailed`
- [ ] Test: path traversal slot_id → `WalletError::InvalidSlotId(String)`

### Starkli-compat keystore

- [x] `StarkliCompat` keystore impl at `crates/octo-wallet/src/keystore.rs` — a unit struct, so the methods take `&self` and the two call sites read `StarkliCompat.import(...)` rather than a bound value
- [x] Format: starkli v0.3+ JSON (Argon2id + chacha20-poly1305)
- [x] **Cipher divergence note:** Starkli uses chacha20-poly1305, NOT AES-256-GCM as RFC-0102 §Key Storage specifies. Implement BOTH: vault = AES-256-GCM (per RFC-0102 post-amendment); starkli import = chacha20-poly1305 (interop only). Document divergence in RFC-0102 §Starkli Keystore Divergence section (added this mission). **OPEN.** The divergence itself is real and the substrate honours it — `StarkliCompat` implements chacha20-poly1305 and `Vault` implements AES-256-GCM — and the §Starkli Keystore Divergence section now lives at L246 of `rfcs/accepted/numeric/0102-wallet-cryptography.md` (after the Key Storage code block) per the m102 box-3 commit (`next 0ba7c89f`). The substrate module header at `crates/octo-wallet/src/keystore.rs` cites the section by name.
- [x] `StarkliCompat::import(&self, path: &Path, passphrase: &str) -> Result<IdentityKey, WalletError>` (reads chacha20-poly1305, decrypts, returns the Ed25519 seed). The earlier form of this box omitted the `passphrase` parameter, which is not a default and not optional.
- [x] `StarkliCompat::export(&self, key, path, passphrase) -> Result<(), WalletError>` (writes chacha20-poly1305 JSON). Same correction: the passphrase parameter was missing.
- [ ] Round-trip test — **the fixture this box names does not exist.** There is no `crates/octo-wallet/tests/fixtures/starkli-v0.3/`; the only fixture directory in the crate is `capability-zk`. What shipped is a **self-round-trip**: each of the three keystore tests exports into a `tempfile::tempdir()` and reads it back. That verifies this crate against itself and proves the envelope is internally consistent. It does **not** verify interop with the real starkli format, which is the only thing a fixture would have established. The next box is the one that would have caught this, and it is unchecked.
- [x] Cross-impl test: export → read with `starkli` CLI if available. **Unchecked**, and it is the criterion that makes the box above's self-round-trip meaningful. Read literally it is weak — `if available` makes it pass vacuously when the tool is absent — so it needs either a hard skip that reports SKIPPED rather than PASSED, or a committed real-starkli fixture that makes the tool unnecessary.

## Notes

- **Substrate split (architectural decision 2026-07-19):** RFC-0102 = Stark Curve; RFC-0009 = Ed25519; RFC-0957 (planned S02) = capability token. Each RFC owns its substrate; wallet crate hosts both.
- **Vault vs Keystore:** Vault = provider-key storage (slot-based, file-per-slot on disk at `~/.config/cipherocto/vault/<slot>.vault`); Keystore = identity-key storage (starkli-compatible JSON, chacha20-poly1305 + Argon2id for interop). Distinct concerns; vault uses AES-256-GCM (per RFC-0102 amendment), starkli uses chacha20-poly1305.
- **Scaffolding policy:** preview files at `crates/octo-wallet/Cargo.toml` + `src/lib.rs` + `src/bin/octo-wallet.rs` exist uncommitted; stubbed with empty module bodies that compile but `unimplemented!()` at runtime. Finalized during claim/implementation phase.
- **RFC-0957 dependency:** capability token format RFC planned for S02. S01 was going to need a `holder_sign` primitive for that; it never built one, and the signing surface it does have is `IdentityKey::sign` plus `IdentityKey::signer`. Full macaroon implementation stays in S02.
- **Mission decomposition (rule trigger acknowledged and overridden):** per BLUEPRINT.md §Mission Lifecycle, the Multi-Mission Decomposition rule, "when an RFC has 10+ types, 4+ phases, or 1000+ lines of specification, decompose into multiple missions". The type table above lists 13 rows, of which **9** are actually implemented in this crate, 2 are assigned to other missions, and 2 were named here but never built (`Identity` and `holder_sign`, both since superseded). The note originally claimed the RFC defines 12 types and that this mission handles all 12; that number matched nothing. The rule is a disjunction of three arms and this RFC crosses one of them — 13 specification types against a threshold of 10, a single phase, and far fewer than a thousand lines — so the type arm fires on 13 and the rule was not followed. An earlier revision of this bullet quoted the rule as "RFC has >10 specification types → decompose", which narrows a three-arm disjunction to its first arm, changes the operator from `10+` to `>10`, and then reasons about the rule on the narrowed form. The conclusion is unchanged and the narrowing is disclosed here rather than left implicit, because a reader checking the quotation against BLUEPRINT would find none of the two versions present in the source. The override is recorded here rather than silently absorbed: the surviving 9 resolve to the one `octo-wallet` crate and were built together over one session, and half the original surface was retired before the PR ever landed, so the decomposition the rule asks for happened by attrition rather than by split. Anyone re-deriving the count should count the table, not this sentence — and should expect it to change again, since two of the rows describe things that will not be built.
- **Identity struct phase-out (open, not done).** The older `Identity { id: String, public_key: [u8; 32] }` struct is superseded inside `octo-wallet` by `IdentityKey`, but the phase-out itself has not happened. `crates/octo-core/Cargo.toml` carries no `octo-wallet` dependency, `crates/octo-core/src/identity.rs` is still in the tree, and `crates/octo-core/src/lib.rs` contains zero occurrences of `IdentityKey`. So all three `octo-core` criteria are unmet: nothing declares the dependency, nothing has been re-exported, and no caller has been migrated. They are the `octo-core` dependency recorded in §Dependencies, and this bullet is the one place that says the work is still ahead — an earlier revision asserted the file was deleted and the callers migrated, in the past tense, while this mission's own §Status and its own three unchecked criteria record the same work as open. A completed tense in a Notes bullet is read as history, which is what makes it the one phrasing that has to be right.
- **What `IdentityKey` actually is.** Neither a newtype nor a wrapper around `ed25519-dalek`. It is a struct whose signing field is `Arc<dyn HsmAdapter>`, holding a raw 32-byte public key beside the lifecycle state and rotation fields. The `ed25519-dalek` dependency sits one layer down, inside `InMemorySigner`, and the crate re-exports `ed25519_dalek` at its own root. The newtype in this module is `CapabilityKey`, a single-field `[u8; 32]` wrapper. An earlier revision of the bullet above described `IdentityKey` as a "newtype wrapping ed25519-dalek", which is the architecture as it stood before the adapter was introduced and is the shape RFC-0009 §HsmAdapter Integration names as host-side seed exfiltration, in the finding recorded there as A9. Getting it backwards is not a naming slip: the adapter is the reason the seed is reachable only through a signing boundary and why a hardware adapter can decline to expose it at all, so a description that puts `ed25519-dalek` at the top of the type asserts the opposite of the property the type exists to have.
