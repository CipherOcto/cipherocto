## 1. Motivation

The numeric parent RFC (`rfcs/accepted/numeric/0105-deterministic-quant-arithmetic.md`) §Asset ID Derivation defines the 9-role-token `ROLE_TOKENS` enumeration (OCTO-A/B/D/M/N/O/S/H/W, sovereign `OCTO` excluded per cross-layer capability-attestation path) and the canonical `asset_id_for` BLAKE3-256 derivation. The vault monetary representation redesign (research doc §3 D1 chain_id partition decision + §9 amendment table row for RFC-0105) drives the **two asset namespaces** framing this RFC adopts:

1. **Sovereign assets** — `OCTO-*` role tokens + their derivatives; managed by octo treasury; chain-independent.
2. **Private assets** — corporate-chain-specific assets; managed by corporate chain operators; chain-bound via `chain_id` segment in the role-token string.

Prior numeric parent (`v2.3`, 2026-08-19) covered only the 9 sovereign `OCTO-*` tokens. v3.0/v3.1 makes the sovereign/private boundary explicit and pins the private-asset derivation path on top of the existing substrate.

## 2. Asset Namespace Specification

### 2.1 Sovereign namespace

| Asset                                                 | Derivation                                                                |
| ----------------------------------------------------- | ------------------------------------------------------------------------- |
| `OCTO-A`                                              | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-A")[:32]`                     |
| `OCTO-B`                                              | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-B")[:32]`                     |
| `OCTO-D`                                              | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-D")[:32]`                     |
| `OCTO-M`                                              | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-M")[:32]`                     |
| `OCTO-N`                                              | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-N")[:32]`                     |
| `OCTO-O`                                              | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-O")[:32]`                     |
| `OCTO-S`                                              | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-S")[:32]`                     |
| `OCTO-H`                                              | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-H")[:32]`                     |
| `OCTO-W`                                              | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-W")[:32]`                     |
| `OCTO-PrivateProvider-Stake` (illustrative extension) | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "OCTO-PrivateProvider-Stake")[:32]` |

**Substrate form:** canonical `asset_id_for(role_token: &str) -> [u8; 32]` (Layer A frozen substrate in external `octo-determin` git-deps crate, no on-disk `crates/` mirror) accepts the 9 sovereign `ROLE_TOKENS` strings verbatim. BLAKE3 input is the **2-component** concatenation `b"cipherocto/asset/v1/"` (constant `ASSET_ID_DOMAIN_V1`) ‖ `role_token.as_bytes()` — no separator is added at the call site beyond the trailing `/` baked into the prefix. The output is the **full 32-byte BLAKE3-256 digest** (no truncation; no byte-0 namespace overwrite).

**Authority:** octo treasury only. Canonical asset_id derivation home is RFC-0105 §Asset ID Derivation (numeric parent).

### 2.2 Private namespace

| Asset                                     | Derivation                                                                             |
| ----------------------------------------- | -------------------------------------------------------------------------------------- |
| `PRIVATE-{chain_id_32B-hex}-{asset_name}` | `BLAKE3-256(b"cipherocto/asset/v1/" ‖ "PRIVATE-{chain_id_32B-hex}-{asset_name}")[:32]` |

**Substrate form:** canonical `asset_id_for(role_token: &str) -> [u8; 32]` is reused with the private-asset role-token string `PRIVATE-{chain_id_32B-hex}-{asset_name}` passed as the `role_token` argument. The substrate has no separate private-asset code path; the namespace distinction lives in the role-token string prefix. BLAKE3 input is the same **2-component** form as §2.1; output is the full 32-byte BLAKE3-256 digest (no truncation; no byte-0 namespace overwrite).

**Cross-RFC drift note (substrate-vs-RFC divergence):** Two pieces of drift between this RFC (substrate-grounded) and adjacent RFCs:

1. **Size drift.** RFC-0206 v3.3 §2.3 references `asset_id_16` as `BLAKE3("cipherocto/asset/v1/" ‖ role_token)[0..16]` (16-byte UUIDv5 truncation form, used in `vault_id` derivation freeze). This RFC (and the substrate, per `crates/octo-vault/src/lib.rs:140`) use the **full 32-byte** form. Substrate is the source of truth for this RFC; consumers reading both MUST NOT assume identical byte lengths.

2. **Byte-0 overwrite drift.** RFC-0206 v3.3 §2.3 (line 100) asserts `asset_id_16[0]` is the **asset-namespace byte** (e.g., `0x01` = Sovereign), overwritten post-BLAKE3 analogous to `chain_id[0]`. This RFC's substrate (`AssetId::derive` at `crates/octo-vault/src/lib.rs:140`) and canonical `octo_determin::asset_id_for` produce a byte vector where `asset_id[0]` is a regular BLAKE3 output byte, **not** a namespace-byte overwrite. The `0x01`/`0x02` semantic (Sovereign/Private) lives in the role-token string prefix (`OCTO-` vs `PRIVATE-`), not in a post-hash overwrite. Consumers implementing `vault_id` derivation from RFC-0206 v3.3 MUST NOT apply a byte-0 namespace overwrite to the asset_id produced by `octo_determin::asset_id_for` (or its `AssetId::derive` wrapper), or the resulting `vault_id` will drift across the corpus. RFC-0206 v3.3 §2.3 byte-0 overwrite claim is **stale relative to this RFC's substrate**; tracked separately.

**Authority:** corporate chain operator (per RFC-0010 §4 Authority Registration Flow). Multiple private assets per chain supported; one chain's `PRIVATE-XYZ` is not portable to another chain's namespace (the `chain_id_32B-hex` segment binds the asset to its origin chain).

### 2.3 Namespace scope clarification

This RFC defines **asset** namespaces (sovereign `OCTO-*`, private `PRIVATE-*`); it does NOT define **chain** namespaces. The two are distinct prefix-collision surfaces:

- **Chain namespaces** — `chain_id[0]` namespace byte (`0x00` Reserved, `0x01` Rfc, `0x02` User, `0x03-0xFF` Reserved) per RFC-0010 §2 `chain_namespace INTEGER NOT NULL` column + §3 `derive_chain_id(namespace, seed)` (RFC-0010 §3 specifies namespace-byte overwrite post-BLAKE3 analogous to the `chain_id[0]` semantics). The `0x00 Reserved` slot is intentionally omitted from the user-assignable range because substrate-side `chain_namespace == 0x00` (NamespaceVariant::Reserved) is REJECTED at read time by `ChainNamespace::from_canonical_bytes` (returns `Err(ChainNamespaceError::ReservedVariant(0x00))`) per RFC-0010 §2 namespace-variant CHECK comment.

- **Asset namespaces** — `OCTO-*` (sovereign) vs `PRIVATE-*` (private) per §2.1 / §2.2 above. The namespace distinction is encoded in the **role-token string prefix**, NOT in a post-hash byte-0 overwrite (see §2.2 cross-RFC drift note for the divergence with RFC-0206 v3.3).

The `0x03-0xFF` Reserved range cited in RFC-0010 §2 is a **chain-namespace** reservation; it does not apply to asset namespaces. Asset-namespace reservations (if any) MUST be specified in a future RFC and MUST NOT collide with chain-namespace values if a composite identifier stores `chain_id` and `asset_id` bytes adjacently (RFC-0206 v3.3 §2.5 cross-RFC semantic collision note).
