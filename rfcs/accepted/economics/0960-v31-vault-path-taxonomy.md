**Accepted (v3.3, 2026-08-23).** Additive to RFC-0960 (2026-08-17).

**Promotion trail:** v3.1 initial draft 2026-08-22 → Accepted 2026-08-22 per long-horizon plan Phase 4 Tier 1 promotion sequence (RFC-0960 v3.1 fourth in Tier 1 = final Tier 1, per research §20 decision #9). ## 1. Motivation

RFC-0960 defines the vault substrate with chain-aware PK `(chain_id, owner_did, asset_id)`. v3.1 adds explicit **path taxonomy**: corporate closed-set vs mesh open-set, sharing the same substrate but distinguishing by chain_id namespace.

## 2. Path Taxonomy

### 2.1 Mesh Open Path

- `chain_namespace = 0x01` (RFC-allocated namespace marker per RFC-0010 §2 ledger_chain_registry Table; substrate `NamespaceVariant::Rfc = 0x01` per `crates/octo-ident/src/chain.rs` §NamespaceVariant impl — "Rfc" covers any RFC-allocated literal, not a specific named chain; `0x00` is REJECTED at read time per `ChainNamespace::from_canonical_bytes` CHECK constraint `chain_namespace >= 0x01`)
- Membership: capability-gated per RFC-0967-A1 §2.6 (`octo/membership/capabilitygated/v1` kind UUID; RFC-0957 defines macaroon substrate + attenuation invariant, NOT the capability-gated MembershipPolicy kind)
- Mint authority: governance-vote or single-key
- Interop default: no-bridge (`octo/interop/none/v1` per RFC-0967-A1 §2.6 kind UUID registry; no substrate-side `octo-interop-no-bridge` crate exists at the time of this RFC's acceptance — the kind UUID is a registry-only identifier)
- Burn default: `octo-burn-time-locked` 24h (FATF Travel Rule + MiCA Article 23 guidance)
- Audit: `octo-audit-mainnet-slim` for v1; A/B for v2

> **Substrate vs RFC alignment (chain_namespace naming, post-R5):** RFC-0010 §2 ledger_chain_registry Table maps `0x01 → Rfc` and `0x02 → User` per `chain_namespace` column comment (R5 fix; byte 0x01 no longer labeled "Mainnet"). Substrate `NamespaceVariant` at `crates/octo-ident/src/chain.rs` §NamespaceVariant impl block uses `0x01 → Rfc` (general — any RFC-allocated literal, covering both `"cipherocto-mainnet"` and `"partner-mainnet"`) and `0x02 → User`. The two sources agree post-R5; cross-validation at registration time uses `chain_metadata.chain_namespace` byte as the source of truth, not the variant name. (No "Mainnet"-specific divergence exists post-R5; pre-R5 RFC-0010 §2 "0x01 Mainnet" label was REMOVED in R5 fix-all per RFC-0010 VH row item (5).)

### 2.2 Corporate Closed Path

- `chain_namespace = 0x02 (User)` per RFC-0010 §2 ledger_chain_registry Table comment (bare parent canonical has no §2/§3 section; bare-RFC-0010 cite resolves to the amendment file via Guard 2 — see note in §5 Cross-References)
- Membership: corp-members-table or capability-gated
- Mint authority: corp-admin (single-key or multisig)
- Interop: opt-in (atomic-swap / wrapped-representation per policy)
- Burn: opt-in to any of `octo-burn-{time-locked,immediate,multisig}`
- Audit: `octo-audit-mainnet-slim` or `octo-audit-testnet-verbose` per corp choice

### 2.3 Same Substrate, Different Policy Bindings

Both paths share:

- `vaults` table (PK `(chain_id, owner_did, asset_id)` per RFC-0960)
- `transfer_events` table (event-sourced per RFC-0960 §2.5; on-disk PK `(chain_id, event_id)` per `crates/octo-vault/migrations/v014__create_transfer_events.sql` line 31; `attributes BLOB` carries the event-type discriminator — there is no `event_type TEXT` column in v014, the §2.5 grand-design prose pre-dates the v014 substrate shape)
- `ValueTransfer` trait (RFC-0206 §3 — RFC-defined trait; substrate-side impl location pending landing via Phase 1 mission 0206-001 v3.0 per RFC-0206 v3.0 §3 explicit annotation; `crates/octo-vault/src/value_transfer.rs` does not exist at the time of this RFC's acceptance — the trait IS defined illustratively in RFC-0206 v3.0 §3 spec block, only the substrate-side impl module is pending)

The path differs only in policy bindings (`chain_metadata` columns — pending substrate landing via Phase 1 mission 0206-001 v3.0 per RFC-0206 v3.0 §4 explicit annotation; only v013 + v014 exist on disk).

## 3. Substrate Migration v017 — additive to v3.0 substrate

`chain_metadata` table augmented (ALTER: new columns on existing table per research doc §8.1 — research doc confirms `chain_metadata` already exists, only new columns are added by v017, NOT a CREATE of a new `chain_metadata` table) per RFC-0010 §3 Chain-id Derivation + §4 Authority Registration Flow + research doc §8.1 — substrate migration pending landing via Phase 1 mission 0206-001 v3.0 per RFC-0206 v3.0 §4 explicit annotation (v017 = chain_metadata ALTER columns + ledger_chain_registry + policy_registry + policy_kind_authority per the single combined file `v017__add_chain_metadata_and_policy_registry.sql`). No change to existing `vaults` or `transfer_events` tables (v013 + v014 already landed on disk); no CREATE of a new `chain_metadata` table.
