## 1. Motivation

RFC-0960 defines the vault substrate with chain-aware PK `(chain_id, owner_did, asset_id)`. v3.1 adds explicit **path taxonomy**: corporate closed-set vs mesh open-set, sharing the same substrate but distinguishing by chain_id namespace.

## 2. Path Taxonomy

### 2.1 Mesh Open Path

- `chain_namespace = 0x01` (RFC-allocated namespace marker per RFC-0010 §2 ledger_chain_registry Table; substrate `NamespaceVariant::Rfc = 0x01` per `crates/octo-ident/src/chain.rs` §NamespaceVariant impl — `0x01` is the variant byte for the canonical pre-registered `"cipherocto-mainnet"` literal only per `RFC_CHAIN_NAMESPACES = &[CIPHEROCTO_MAINNET_TAG]`; substrate `ChainNamespace::from_canonical_bytes` is a Rust runtime match that REJECTS `0x00` AND `0x03-0xFF` with `Err(ChainNamespaceError::ReservedVariant(v))` per `octo-ident/src/chain.rs` `from_canonical_bytes_rejects_reserved_variant` test; the substrate-side SQL CHECK is `chain_namespace = x'01' OR chain_namespace = x'02'` per RFC-0010 §2 `ledger_chain_registry` DDL)
- Membership: capability-gated per RFC-0967-A1 §2.6 (`octo/membership/capabilitygated/v1` kind UUID; RFC-0957 defines macaroon substrate + attenuation invariant, NOT the capability-gated MembershipPolicy kind)
- Mint authority: governance-vote or single-key
- Interop default: no-bridge (`octo/interop/none/v1` per RFC-0967-A1 §2.6 kind UUID registry; no substrate-side `octo-interop-no-bridge` crate exists at the time of this RFC's acceptance — the kind UUID is a registry-only identifier)
- Burn default: `octo/burn/timelock/v1` 24h (FATF Travel Rule + MiCA Article 23 guidance)
- Audit: `octo/audit/mainnet/v1` for v1; `octo/audit/ab/v1` for v2

> **Substrate vs RFC alignment (chain_namespace naming, post-R5):** RFC-0010 §2 ledger_chain_registry Table maps `0x01 → Rfc` and `0x02 → User` per `chain_namespace` column comment (R5 fix; byte 0x01 no longer labeled "Mainnet"). Substrate `NamespaceVariant` at `crates/octo-ident/src/chain.rs` §NamespaceVariant impl block uses `0x01 → Rfc` and `0x02 → User`; the `Rfc` variant is returned ONLY when the input tag is a member of `RFC_CHAIN_NAMESPACES` (currently just `CIPHEROCTO_MAINNET_TAG = "cipherocto-mainnet"`; arbitrary RFC-named literals such as `"partner-mainnet"` return `NamespaceVariant::User`, NOT `Rfc`, per `octo-ident/src/chain.rs` `from_namespace_tag` impl block + `partner-mainnet → User` test). Two sources (RFC-0010 §2 + substrate `NamespaceVariant` impl) agree post-R5 on `0x01 → Rfc` / `0x02 → User` byte mapping; cross-validation at registration time uses `chain_metadata.chain_namespace` byte as the source of truth, not the variant name. (RFC-0010 §2 "0x01 Mainnet" label was REMOVED in R5 fix-all per RFC-0010 VH row item (5); **residual drift sources still carrying the obsolete "Mainnet" label post-R5** are `docs/research/2026-08-21-vault-monetary-representation-redesign.md` §8.1 chain_metadata DDL column comment (`-- 0x01=Mainnet, 0x02=User, 0x03-0xFF=Reserved`) and `rfcs/accepted/process/0206-v33-value-transfer-canonicalization.md` §2.5 disambiguation table (`0x01 = Mainnet`) — both labeled LIVE drift and out of scope of this RFC to edit, but documented here so the §2.1 alignment header does not overstate "all sources harmonized".)

### 2.2 Corporate Closed Path

- `chain_namespace = 0x02 (User)` per RFC-0010 §2 ledger_chain_registry Table comment (bare parent canonical has no §2/§3 section; bare-RFC-0010 cite resolves to the amendment file via Guard 2 — see note in §5 Cross-References)
- Membership: corp-members-table or capability-gated
- Mint authority: corp-admin (single-key or multisig)
- Interop: opt-in (atomic-swap / wrapped-representation per policy)
- Burn: opt-in to any of `octo/burn/{timelock,immediate,multisig}/v1`
- Audit: `octo/audit/mainnet/v1` or `octo/audit/testnet/v1` per corp choice

### 2.3 Same Substrate, Different Policy Bindings

> Forward-reference: see RFC-0960 §2 Specification for the vault-balance projection substrate; the projection PK `(chain_id, vault_id)` is a STRICT SUBSET of this section's `(chain_id, owner_did, asset_id)` PK.

Both paths share:

- `vaults` table (PK `(chain_id, owner_did, asset_id)` per RFC-0960)
- `transfer_events` table (event-sourced per RFC-0960 §2.5; on-disk PK `(chain_id, event_id)` per `crates/octo-vault/migrations/v014__create_transfer_events.sql` §Primary Key clause; `attributes BLOB` carries the event-type discriminator — there is no `event_type TEXT` column in v014, the §2.5 grand-design prose pre-dates the v014 substrate shape)
- `ValueTransfer` trait (RFC-0206 §3 — RFC-defined trait; substrate-side impl location pending landing via Phase 1 mission `vault-chain-metadata` per research doc §16; `crates/octo-vault/src/value_transfer.rs` does not exist at the time of this RFC's acceptance — the trait IS defined illustratively in RFC-0206 §3 spec block, only the substrate-side impl module is pending)

The path differs only in policy bindings (`chain_metadata` columns — pending substrate landing via Phase 1 mission `vault-chain-metadata` per research doc §16; only v013 + v014 exist on disk).

## 3. Substrate Migration v017 — additive to v3.0 substrate

`chain_metadata` table created fresh by v017 per `docs/research/2026-08-21-vault-monetary-representation-redesign.md` §8.1 chain_metadata DDL block (research doc §8.1 uses `CREATE TABLE chain_metadata (...)` syntax, NOT ALTER — the table does not yet exist on disk per `RFC-0206 §4` `v017` migration enumeration which lists `chain_metadata` as one of four tables added by the single combined migration) per RFC-0010 §3 Chain-id Derivation + §4 Authority Registration Flow + research doc §8.1 — substrate migration pending landing via Phase 1 mission `vault-chain-metadata` per research doc §16 (v017 = chain_metadata + ledger_chain_registry + policy_registry + policy_kind_authority per the single combined file `v017__add_chain_metadata_and_policy_registry.sql`). No change to existing `vaults` or `transfer_events` tables (v013 + v014 already landed on disk); `chain_metadata` does NOT yet exist on disk.

> **Substrate-vs-RFC framing note (v017 chain_metadata DDL):** Sibling Accepted RFC-0010 §2 corrected framing from ALTER to CREATE in its R7 fix-all row item (7) per research doc §8.1 CREATE TABLE syntax; this RFC §3 R7 row initially carried an ALTER gloss that R7 reviewers flagged as contradictory with research doc §8.1 + RFC-0010 §2 (sibling amendment substrate status block). This v3.4 row corrects the framing to CREATE per RFC-0010 §2 + research doc §8.1 (two sources agree on CREATE; ALTER is unsubstantiated by any cited substrate or RFC source). The §3 parenthetical "substrate migration pending landing via Phase 1 mission 0206-001 v3.0 per RFC-0206 §4" was also updated to reference mission `vault-chain-metadata` per research doc §16 (0206-001 is Layer A storage-core, not vault DDL).
