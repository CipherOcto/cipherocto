## 1. Motivation

RFC-0010 defines Canonical OctoID Identifier Codec. v1.7 adds a **chain_id registration authority** — the substrate-side mechanism by which corporate chains obtain `chain_id: [u8;32]` values within the `0x02 (User)` namespace.

## 2. ledger_chain_registry Table

> **Substrate status:** DDL below is the **spec** for the `ledger_chain_registry` table portion of migration `v017__add_chain_metadata_and_policy_registry.sql` per RFC-0206 v3.0 §Substrate Migration v015–v018 — **pending landing via Phase 1 mission `vault-chain-metadata` per research doc §16**. No SQL migration file exists on disk yet under `crates/octo-*/migrations/` (verified: only `v013__create_vaults.sql` + `v014__create_transfer_events.sql` present in `crates/octo-vault/migrations/`). The `chain_metadata` reference here is a substrate-vs-RFC divergence: research doc §8.1 uses `CREATE TABLE chain_metadata (...)` syntax (table does not yet exist on disk), while this RFC §2 previously framed the change as ALTER-on-existing — the framing is corrected here per R7 fix-all: the underlying v017 migration creates the `chain_metadata` table fresh per research doc §8.1, not ALTER. Substrate consumers must treat this section as the binding spec for the `ledger_chain_registry` table portion only — the other 3 tables in the v017 combined migration (chain_metadata columns + policy_registry + policy_kind_authority) are specified in research doc §8.1 + §8.2 and out of scope for this RFC §2.
>
> **Substrate-vs-RFC filename drift:** This RFC §2 historically named two v017 migration files (`v017__create_ledger_chain_registry.sql` + `v017__create_chain_metadata.sql`); RFC-0206 v3.0 §Substrate Migration v015–v018 names one combined file (`v017__add_chain_metadata_and_policy_registry.sql` covering 4 tables). The canonical filename per RFC-0206 v3.0 §Substrate Migration v015–v018 wins — operators applying this RFC's DDL MUST use the single combined filename to avoid the cross-RFC acceptance chain divergence flagged by R4 review.

```sql
CREATE TABLE ledger_chain_registry (
    chain_id BLOB(32) NOT NULL PRIMARY KEY,
    chain_namespace BLOB(1) NOT NULL,  -- 0x01 Rfc / 0x02 User; per substrate ChainNamespace::from_canonical_bytes which accepts only 0x01/0x02 and rejects ALL other values (including 0x00 and 0x03-0xFF) as Err(ChainNamespaceError::ReservedVariant(v)); CHECK below narrows to substrate-acceptable values only per R7 fix-all.
    operator_did BLOB(32) NOT NULL,
    operator_signature BLOB(64) NOT NULL,  -- Ed25519 over canonical-serialized registration body
    registration_body BLOB NOT NULL,        -- canonical CBOR: chain_name, contact_uri, policy_hashes
    registered_at_unix INTEGER NOT NULL,
    revoked_at_unix INTEGER,                -- NULL = active
    CHECK (length(chain_id) = 32),
    CHECK (length(chain_namespace) = 1),
    -- Substrate-side: chain_namespace byte is REJECTED at read time by `ChainNamespace::from_canonical_bytes`
    -- if not 0x01 or 0x02 (returns `Err(ChainNamespaceError::ReservedVariant(v))`).
    -- CHECK below mirrors research doc §8.1 (R11 fix F-R11-CHAIN-NAMESPACE-0X00-PHANTOM): only 0x01 + 0x02 permitted.
    CHECK (chain_namespace = x'01' OR chain_namespace = x'02'),
    CHECK (length(operator_signature) = 64)
);

CREATE UNIQUE INDEX ledger_chain_registry_active_op_idx ON ledger_chain_registry(operator_did) WHERE revoked_at_unix IS NULL;
```

> **Substrate-vs-RFC column-type divergence:** This RFC §2 specifies `chain_namespace BLOB(1)` (single-byte blob). **Research doc §8.1 §chain_metadata column comment** uses `CHECK chain_namespace >= 0x01 AND chain_namespace <= 0xFF` (allowing 0x03-0xFF as `Reserved`); this RFC §2 narrows the CHECK to `(chain_namespace = x'01' OR chain_namespace = x'02')` per substrate `ChainNamespace::from_canonical_bytes` which rejects all values outside {0x01, 0x02} as `Err(ChainNamespaceError::ReservedVariant(v))`. The research doc §8.1 wider CHECK (0x03-0xFF allowed) and this RFC §2 narrower CHECK (0x01/0x02 only) are an unclosed cross-RFC drift — operators migrating per research doc §8.1 verbatim would accept `chain_namespace = 0x03` at DDL time only to have substrate reject it at read time. Substrate-binding form: this RFC §2 narrow CHECK. **Substrate behavior (per octo-ident/src/chain.rs §from_canonical_bytes):** `pub fn from_canonical_bytes(bytes: &[u8; 17]) -> Result<Self, ChainNamespaceError>` — the 17-byte canonical encoding is the `ChainNamespace` literal-derived form (1 byte variant + 15 bytes tag + 1 byte length), NOT `chain_id[32]`. `ChainId` is the 32-byte BLAKE3 hash (no namespace byte at any position); `ChainNamespace` is the separate 17-byte literal-derived canonical encoding. `ChainId::namespace()` derives `ChainNamespace` from the literal string, NOT from `chain_id[0]`. This RFC §2 column-type divergence header therefore describes two SEPARATE substrate types, not a single `chain_id[0]` field. The CHECK constraint above ensures SQL-level and substrate-level agreement so an INSERT with `chain_namespace = 0x03` is rejected at DDL time (rather than passing DDL and failing at substrate read time).

## 3. Chain-id Derivation

> **Substrate vs RFC divergence (RFC-level extension):** Substrate carries **TWO parallel** canonical chain-id BLAKE3 derivations, both producing `BLAKE3(b"cipherocto/chain/v1/" || chain_string_bytes)`. Neither takes a namespace parameter, neither overwrites byte 0, and **neither hex-encodes the input** (both hash raw input bytes):
>
> 1. `octo_ident::ChainId::as_bytes(&self) -> [u8;32]` (octo-ident/src/chain.rs `ChainId::as_bytes` impl; wraps `&String` inner field). Carries the canonical chain-id BLAKE3 derivation introduced in parent RFC-0010 v1.6 32-byte Addendum amendment.
> 2. `octo_vault::ChainId::derive(chain_string: &str) -> Self` (octo-vault/src/lib.rs `ChainId::derive` impl; wraps `[u8;32]` inner field). Active in 11 test sites (`octo-vault/tests/apply_migrations.rs` [1 call site] + `crates/octo-vault/examples/capture_tv_v1.rs` [1 call site; examples/, not tests/] + `octo-vault/tests/test_vectors.rs` [3 call sites] + the substrate impls themselves at `octo-vault/src/lib.rs` [6 call sites]) + the v013 SQL migration header (the v014 header does NOT reference chain_id derivation).
>
> Both derive **identical 32-byte BLAKE3 output** (same domain tag `cipherocto/chain/v1/` + same input bytes); the wrappers diverge in inner representation (`String` vs `[u8;32]`) but the BLAKE3 digest is canonical. Both produce 32 raw BLAKE3 bytes from **raw input bytes (no hex encoding)** — **no namespace-byte overwrite**.
>
> This RFC §3 `derive_chain_id(namespace, seed)` is an **RFC-defined extension pending substrate landing**. It exists because the registration-authority flow needs (a) namespace-parameterized derivation for namespace isolation, and (b) seed-slice input for corporate-operator registration bodies. Corporate operator clients implementing the §4 registration flow MUST use this RFC §3 form (with hex encoding and overwrite) so that `chain_id[0]` carries the namespace discriminant; substrate callers using either `octo_ident::ChainId::as_bytes` or `octo_vault::ChainId::derive` use the substrate form (raw bytes, no hex encoding, no overwrite). The two forms are intentionally divergent on **TWO axes**: hex-encoding input (RFC vs substrate) AND byte-0 overwrite (RFC vs substrate); cross-validation at registration time is intended to use `chain_metadata.chain_namespace` as the source of truth, not `chain_id[0]` — **BUT `chain_metadata` itself does not yet exist on disk** (no v017 migration landed; verified by absence of `v017__add_chain_metadata_and_policy_registry.sql` in `crates/octo-vault/migrations/`). Until substrate lands, the §3 contract is asymmetric: the runtime invariant is asserted but unfulfillable; registration flow must fall back to substrate-side `ChainNamespace` validation via the substrate forms (`octo_ident::ChainId::as_bytes` / `octo_vault::ChainId::derive`), with the `chain_metadata` cross-validation deferred to post-v017 substrate landing. **Cross-RFC drift notes:** (a) research doc §8.1 carries the same `0x01=Mainnet` wording drift against substrate `NamespaceVariant::Rfc = 0x01` already noted in this RFC §3 cite loop; (b) RFC-0206 v3.3 §2.3 + §2.5 claim substrate overwrites `chain_id[0] = namespace as u8` post-BLAKE3, which contradicts this RFC §3 (substrate does NOT overwrite byte 0) — RFC-0206 v3.3 should be amended to remove the byte-0 overwrite claim and align with substrate semantics.

```rust
// RFC-level extension (pending substrate landing). Substrate `ChainId::as_bytes` is the
// canonical BLAKE3 derivation; this function extends that surface for namespace-parameterized
// corporate-operator registration per §4. See header note above for divergence rules:
// (a) RFC hex-encodes input, substrate does not; (b) RFC overwrites byte 0 with namespace
// variant byte post-BLAKE3, substrate does not.
fn derive_chain_id(namespace: ChainNamespace, seed: &[u8]) -> [u8;32] {
    let input = format!("cipherocto/chain/v1/{}", hex::encode(seed));
    let hash = blake3(input.as_bytes());
    let mut out = [0u8;32];
    out.copy_from_slice(&hash.as_bytes()[..32]);
    // Namespace byte OVERWRITES byte 0 post-BLAKE3 (per RFC-0206 v3.3 §2.5 namespace-byte
    // disambiguation table; the §2.5 table row 0x01 reads "Mainnet" in some copies of the
    // table, a term that does not appear in substrate `NamespaceVariant::Rfc = 0x01` —
    // substrate and this RFC both use "0x01 Rfc", and the §2.5 table wording is
    // drift noted here per R7 fix-all). Substrate-binding form: `ChainNamespace` has no
    // `as u8` impl — the variant byte is exposed via `namespace.variant()` returning
    // `NamespaceVariant` (which has `as_byte() -> u8` per octo-ident/src/chain.rs
    // §NamespaceVariant impl block).
    out[0] = namespace.variant().as_byte();
    out
}
```

**Collision resistance:** BLAKE3 32-byte hash provides ~248-bit pre-image + ~124-bit collision resistance on bytes `[1..32]` (31 bytes of BLAKE3 output are operator-input-dependent; the full 32-byte BLAKE3 output has ~128-bit collision resistance, but byte 0 is operator-controlled post-BLAKE3 and serves as the namespace discriminant, reducing the hash-derived surface to 31 bytes = 248 bits → birthday bound 2^124). Byte 0 is not part of the collision surface. For corporate chains, the seed is `corp_did || corp_seed` (corp_seed is operator-controlled entropy).

## 4. Authority Registration Flow

```
1. Operator computes candidate chain_id via derive_chain_id(
       ChainId::new("cipherocto/chain/v1/<namespace_tag>")?.namespace()?,
       corp_did || corp_seed
   ) (this RFC §3 form; uses the public substrate constructor `ChainId::new(literal)?.namespace()?`
   because the `ChainNamespace` struct-literal form has all three fields PRIVATE per
   octo-ident/src/chain.rs §ChainNamespace struct definition; the `0x02` namespace-byte
   shorthand maps to NamespaceVariant::User per octo-ident/src/chain.rs §NamespaceVariant enum)
2. Operator queries ledger_chain_registry for chain_id collision (returns None if available)
3. Operator signs registration_body (chain_name, contact_uri, policy_hashes) with operator_pubkey
4. Operator submits INSERT into ledger_chain_registry via substrate migration
5. Runtime application code (NOT the SQL migration) verifies signature against operator_did
   via RFC-0009 Ed25519 verifier before the INSERT is dispatched. SQL migrations execute
   as static DDL/DML and cannot perform cryptographic verification — sig check is an
   application-runtime concern; migration only enforces the static CHECK + UNIQUE constraints.
6. Substrate accepts INSERT (UNIQUE constraint enforces single-active-per-operator)
```
